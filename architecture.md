# cajita — architecture

Status: **v0.33** · 2026-10-23 · S28 content-space masks, natural mask aspect, copy cleanup.

This is the structural map. It defines what lives where, what is pure, what is
allowed to touch the browser or a native shell, and how state moves through the
app. When this document and the code disagree, either the code is wrong or this
document gets amended in the same change. There is no third option.

---

## 1. What cajita is

cajita is a local-first authoring tool for small, hypertextual, static websites:
portfolios, interactive comics, digital-humanities collections, scrapbooks,
moodboards, tiny personal sites.

One project is one site. A site is a set of **pages**, each page is a **stage**
with a fixed aspect ratio, and each stage holds **elements** (text, image, video,
sound). Elements can link to another page or to an external URL. The whole thing
exports as a normal folder of static HTML, CSS, media, and a tiny progressive
enhancement script. It can be published to GitHub Pages without a server.

The name is the metaphor: a cigar box of cut-outs, stickers, index cards, and
tape. The tool should feel like opening that box, not like opening a dashboard.

### v1 non-goals

These are not "later, if there is time" nice-to-haves. They are actively out of
scope for v1 because they would change the model or the aesthetic:

- a general-purpose CMS, blog engine, or e-commerce tool;
- free-form responsive layout building with breakpoints;
- a code editor, raw HTML/JS embeds, or a scripting language;
- cloud accounts, collaboration, comments, analytics, tracking;
- rich text with per-word formatting (v1 text is one voice per text element);
- themes/plugins marketplaces;
- uploading arbitrary fonts (v1 ships a curated, licensed set);
- native mobile editing.

Some of these become possible later without breaking the core. The line matters:
if a feature can be added as another element type, another exporter, or another
platform adapter, it is probably safe. If it requires pages to stop being stages,
it is a different product.

## 2. Non-negotiable principles

1. **The export is the product.** The preview is generated by the same code as
   the export, inside an iframe. If the preview looks right and the export does
   not, that is a bug in one pipeline, not an acceptable difference.
2. **Local-first.** The working copy lives in the browser (IndexedDB). A
   `.cajita` bundle is the portable backup. Nothing is uploaded until the user
   presses _publish_.
3. **Constraints are features.** Curated stage sizes, palettes, fonts, layout
   modes, and element types. Every new control must earn its place.
4. **Direct manipulation.** The page is the editor. Panels are for precision,
   not for replacing the canvas.
5. **Pure core, thin edges.** Domain code is plain JavaScript (ESM): no Svelte, no DOM,
   no network, no `Date.now()` or `Math.random()` unless injected. Platform code
   is the only place that knows about IndexedDB, `fetch`, files, or Electron-like
   shells.
6. **One geometry.** The editor and the exporter share the same frame math and
   the same CSS-variable generator. There is exactly one definition of where an
   element is.
7. **Never lose a student's work silently.** Autosave, undo, explicit backups,
   validated imports, atomic writes where the platform allows it, and a token
   that never leaves the device.
8. **Bilingual from the first commit.** Every UI string goes through `t()`;
   Spanish and English ship together; missing keys fail the test suite.
9. **Light dependencies.** No UI kit, no graph library, no drag-and-drop
   framework, no heavy state library. Small, auditable packages only.
10. **Accessible static output.** The exported site works without JavaScript for
    reading and navigation; metadata is native `<details>`; every image can have
    alt text; focus is always visible.

```
│  (document + history) (selection/tool)  (panels/toasts) (long jobs)     │
└───────────────▲──────────────────────────────────┬──────────────────────┘
                │ snapshots, results               │ pure calls
┌───────────────┴──────────────────────────────────▼──────────────────────┐
│  domain/  (pure JavaScript, unit-tested)                                │
│  model · geometry · links · history · thumbnails · export · publish     │
└───────────────▲──────────────────────────────────┬──────────────────────┘
                │ Blobs, bytes, URLs               │ interfaces
┌───────────────┴──────────────────────────────────▼──────────────────────┐
│  platform/                                                              │
│  web: IndexedDB · Blob · File System Access (optional) · fetch · zip    │
│  desktop (later): Electrobun RPC · fs · keychain · native dialogs       │
└─────────────────────────────────────────────────────────────────────────┘
```

**Dependency rule:** arrows point inward. `domain/` imports nothing from `state/`,
`platform/`, or `components/`. `state/` imports `domain/` and platform interfaces.
`components/` imports `state/` and read-only domain helpers. `platform/web/` is
the only code allowed to import `idb`, `fflate`, or call `fetch` for GitHub.

If a domain function needs a browser measurement (for example, the natural
height of a text block), it does not get one. The UI measures and passes the
number in; the domain stays pure.

## 4. Stack and repository shape

### Chosen stack

| Concern         | Choice                   | Why                                                          |
| --------------- | ------------------------ | ------------------------------------------------------------ |
| UI              | Svelte 5 (runes)         | Your stack; excellent for direct manipulation; small runtime |
| Build           | Vite + JavaScript (ESM)  | Fast, simple, and readable; JSDoc for data shapes            |
| Package manager | Bun (already installed)  | Fast installs, matches comiquero/Electrobun, Node-compatible |
| Tests           | Vitest                   | Pure domain tests, no browser needed                         |
| ZIP             | `fflate`                 | Small, fast, works in browser and Bun                        |
| IndexedDB       | `idb`                    | Tiny typed wrapper; avoids a bespoke bug farm                |
| Icons           | custom inline SVG sprite | Keeps the visual language consistent                         |
| UI kit          | none                     | The aesthetic is the product; generic kits fight it          |

No SvelteKit. The editor is a single application shell with a small amount of
internal view state (project picker, editor, preview, publish). File-based routes
would add SSR configuration, adapter ceremony, and `%sveltekit%` indirection for
no user-visible benefit. If a marketing/docs site is needed later, it can live in
a separate folder or be added with Vite multi-page input. This decision is
reversible at low cost.

The repository is PolyForm Noncommercial 1.0.0 (`LICENSE`). The **output** a user creates
(the exported site and its media) belongs to the user; cajita is a tool, not a
license that spreads to their work. State this in the README and the About panel.

## 5. Document model

### Hierarchy

**cajita** is the application. A **project** is one site; its portable file is a
`.cajita` bundle. A project contains **pages**; a page is a stage with **elements**
(text, image, video, audio). Assets, custom fonts, redirects, and publish settings
belong to the project. Links belong to elements and connect pages.

```
cajita (app)
└─ project (one site, saved as .cajita)
   ├─ pages (stage, layout, background, transition)
   │  └─ elements (text, image, video, audio)
   │     ├─ link (page / URL / ficha)
   │     └─ metadata
   ├─ assets (images, video, audio)
   ├─ custom fonts
   ├─ redirects (bounded, max 5)
   └─ publish settings (no token)
```

Do not call a project a "cajita" in the UI. The app is cajita; the thing the
student opens, saves, and publishes is a project.

The model is deliberately boring and serialisable. No class instances, no Blobs,
no functions, no DOM references. Everything can be written to JSON, diffed, and
inspected in a bug report.


Platform-only types (`ProjectSummary`, `SiteFile`, `SaveResult`, `GitHubRequest`,
`GitHubResponse`) live in `src/lib/platform/types.js`. They never appear inside
`Project`.

### Model rules

- **IDs are permanent.** `p_`, `el_`, `a_` + `crypto.randomUUID()`. Never reuse
  an ID. Duplicating an element creates a new ID.
- **Internal links point to page IDs, never slugs.** Renaming a slug therefore
  cannot break internal links. Slugs are resolved only at export time.
- **The start page is `project.startPageId`.** Deleting it must select or create
  another page in the same command; the project is never without a start page.
- **Slugs are unique and reserved.** Lowercase, accents transliterated, only
  `[a-z0-9-]`, no leading/trailing hyphen. Reserved: `assets`, `index`, `404`,
  `cajita`, `sitemap`, `robots`. The start page is exported as `index.html`; its
  slug is still a normal slug used for display and for the map.
- **Redirects are a bounded FIFO queue, max 5 per project.** Renaming a slug
  pushes `{ from: oldSlug, toPageId, createdAt }` to `project.redirects`; if the
  queue exceeds 5, the oldest entry is dropped. A new entry whose `from` is now a
  live slug removes the stale redirect (the live page wins); deleting a page
  removes redirects that point to it. The exporter writes a tiny stub for each
  entry. Older than the last five renames → 404, which is an acceptable trade for
  a lean project.
- **Frames are in stage design pixels**, before rotation, rotation around the
  frame centre. Resizing the stage scales every frame and grid margin/gutter
  proportionally; the command then re-snaps grid pages. This is a pure function.
- **Text is plain text.** One font, size, colour, alignment per element. Newlines
  are preserved. No per-run bold/italic/links in v1. That is a constraint, not a
  missing feature.
- **Custom fonts are project assets.** Max two per project, 5 MB each, TTF/OTF/
  WOFF/WOFF2, no SVG fonts. `project.fonts[id]` records name, weight, style, and
  the license attestation; the bytes are an asset of kind `font`. A font used by
  any text element cannot be deleted; replace it first. Custom fonts are included
  in the bundle and the exported site only when used.
- **Redirects are not page data.** They are a project-level FIFO queue (max 5),
  because the interesting history is the last few renames, not every page's
  entire past. This keeps the project JSON small and the export lean.
- **One action per element.** `link` is either a page, an external URL, or the
  metadata card. This avoids the classic "does clicking navigate or open info?"
  ambiguity and keeps the export markup simple. `kind: 'meta'` requires a
  non-empty `meta`; page targets must exist; URLs are sanitised.
- **At most one heading per page.** A text element may set `heading: true`. If
  none does, the exporter emits a visually hidden `<h1>` with the page title.
  Two headings on one page is a validation error, not a silent duplicate.
- **Assets are immutable.** Replacing an image creates a new asset; the old one
  is garbage-collected only when nothing references it and the user asks, or on
  project bundle export. Undo therefore always has its bytes.
- **No Blobs in `Project`.** Binary data lives in the asset repository, keyed by
  asset ID. The project JSON can be stringified at any time.
- **Timestamps only where meaningful.** `createdAt`/`updatedAt` are not injected
  into exported HTML by default, so exports are deterministic.

### Link graph is derived

There is no separate edges table. The graph is a pure projection of pages and
element links:

```ts
// src/lib/domain/links.js
export interface LinkEdge {
  pageId: Id;
  elementId: Id;
  target: LinkTarget;
}
export interface LinkGraph {
  nodes: Array<{ pageId: Id; title: string; slug: string; start: boolean }>;
  edges: LinkEdge[];
  orphans: Id[]; // pages with no inbound and not start
  broken: LinkEdge[]; // page target no longer exists
}
export function buildLinkGraph(project: Project): LinkGraph;
```

This is also the data source for the **Map** view (pages as cards, links as
wires) and for "orphan page" warnings. One source of truth, no sync bugs.

### Versioning and migrations

`Project.version` is an integer. `parseProject(raw)`:

1. rejects non-objects and wrong `format`;
2. applies migrations in order (`v1 → v2 → ...`) as pure functions;
3. validates required fields and invariants;
4. returns a `Result<Project, ImportError[]>` with human-readable paths.

Never silently `any`-cast an imported file. Invalid files are rejected with a
message that names the field; partially valid files are **not** imported.

## 6. State, commands, and events

### Stores

| Store                   | Persisted?         | Contents                                                                   |
| ----------------------- | ------------------ | -------------------------------------------------------------------------- |
| `project.svelte.js`     | yes, debounced     | `Project`, history, dirty flag, last saved                                 |
| `editor.svelte.js`      | no                 | active page, selection, tool, zoom, pan, view (`page`/`map`), text editing |
| `ui.svelte.js`          | no                 | open panels, dialog, toasts, command palette                               |
| `jobs.svelte.js`        | no                 | active export/publish jobs and progress                                    |
| `preferences.svelte.js` | yes (localStorage) | locale, panel widths, last project id, reduced motion override             |

Svelte 5 runes are used for all reactive state. `$derived` computes selections,
the active page, the link graph, used fonts, and export summaries. `$effect` is
reserved for DOM side effects and autosave scheduling; it is **not** used to keep
two copies of the model in sync.

### Commands

All document mutations go through a command. Components never assign to
`project.pages[...]` directly.

```ts
// src/lib/state/project.svelte.js (shape)
export interface CommandOptions {
  label: string;              // shown in the UI, e.g. "mover elemento"
  coalesceKey?: string;       // e.g. "move:el_123" — merge repeated moves
}

export const projectStore = {
  project,                    // $state<Project>
  canUndo, canRedo,
  undo(), redo(),
  run<T>(options: CommandOptions, mutate: (draft: Project) => T): T,
  // named commands built on run():
  addPage(), deletePage(), reorderPages(), setStartPage(),
  addElement(), deleteElements(), updateElement(), moveElements(),
  setLink(), unlink(), addAsset(), removeAsset(),
};
```

`run()` snapshots the project **before** the mutation, applies the mutator to a
structured clone, validates the result, commits it, and pushes a history entry.
With Svelte 5 that means `structuredClone($state.snapshot(project))`, never
`structuredClone(project)` on the proxy itself. For pointer-driven operations
(drag, resize, rotate, sliders), the UI calls `updateElement` with a
`coalesceKey`; history merges consecutive entries with the same key inside a
600 ms window. One drag = one undo step.

The history is a bounded stack (default 40 entries) of `Project` snapshots. It
does not include assets (immutable) or UI state. Memory is therefore small even
for 50 pages.

### Selection is not document state

`editorStore.selection: Id[]` is ephemeral. It is not saved, not exported, and
not part of undo. If an element is deleted, the command prunes it from the
selection. If a page is deleted, the active page changes in the same command.

### Long jobs

Export and publish can take seconds. They are modelled as jobs:

```ts
export type JobKind = 'export.site' | 'export.bundle' | 'publish.github';
export type JobState = 'queued' | 'running' | 'done' | 'failed' | 'cancelled';

export interface Job {
  id: string;
  kind: JobKind;
  state: JobState;
  stage: string; // "render", "zip", "upload", "pages-build"
  current: number;
  total: number; // 0 = indeterminate
  message?: string;
  error?: AppError;
}
```

A small typed bus (same pattern as comiquero's `job-bus.js`) lets the dialog
subscribe to progress and await a terminal event. Terminal events are retained
until consumed so a fast job cannot finish between receiving its ID and
subscribing. Jobs can be cancelled where the platform allows it (ZIP, upload,
Pages polling); DOM rendering is not cancellable and should not pretend to be.

### No global DOM event bus

There is no `window.dispatchEvent` for application events. UI actions call
commands and receive results; cross-cutting concerns use stores. The only
messages between the app and the preview iframe are a tiny, versioned
`postMessage` protocol (`cajita:preview:ready`, `cajita:preview:navigate`,
`cajita:preview:close`). This keeps debugging possible and avoids action at a
distance.

## 7. Geometry and rendering

### The stage coordinate system

Every page has a design space of `stage.width × stage.height` (default
1200 × 800). Element frames are in that space. The editor scales the whole stage
to fit the available viewport; it does **not** reflow elements. The exported site
does the same with CSS.

This is the Decker/Bitsy/Hotglue constraint: a page is a composed surface, not a
liquid layout. It makes collage, comics, and precise compositions possible, and
makes the exported HTML dramatically simpler and more predictable.

Two fit modes cover most needs:

- `contain` — the whole stage is visible, letterboxed. Best for comics, posters,
  square collages, 16:9 stages.
- `width` — the stage fills the browser width and the page scrolls vertically.
  Best for portrait stages, long scrapbook pages, reading.

A future `flow` page type (responsive, document-like) is explicitly deferred. It
would be a different renderer, not a fourth layout mode.

### Shared frame math

```ts
// src/lib/domain/geometry.js
export interface StageRect {
  width: number;
  height: number;
}

/** Convert a frame to the CSS custom properties used by BOTH editor and export. */
export function frameToCss(
  frame: Frame,
  stage: StageRect
): {
  '--x': string; // "12.5%"  (left, % of stage width)
  '--y': string; // "18%"    (top, % of stage height)
  '--w': string; // "30%"    (% of stage width)
  '--h': string; // "42%"    (% of stage height)
  '--rot': string; // "-4deg"
};

/** Geometry plus the per-element presentation vars used by the exporter. */
export function elementToCss(
  element: Element,
  stage: StageRect
): {
  '--x': string;
  '--y': string;
  '--w': string;
  '--h': string;
  '--rot': string;
  '--z': string;
  '--opacity': string;
};

/** Font size in container query width units, so text scales with the stage. */
export function pxToCqw(px: number, stageWidth: number): string; // "2.6667cqw"

/** Resize a (possibly rotated) frame from a handle, in stage coordinates. */
export function resizeFrame(
  frame: Frame,
  handle: 'nw' | 'n' | 'ne' | 'e' | 'se' | 's' | 'sw' | 'w',
  pointer: { x: number; y: number },
  options: { keepAspect: boolean; fromCenter: boolean; minSize: number }
): Frame;

export function rotateFrame(
  frame: Frame,
  pointer: { x: number; y: number },
  snap: number
): Frame;
export function normaliseAngle(deg: number): number; // (-180, 180]
```

The editor positions elements with percentages inside a stage whose aspect ratio
is fixed. Rotation uses `transform: rotate()`. Handles live in an overlay layer
that is **not** rotated with the element, so their screen size stays constant at
any zoom. Handle hit-testing converts the pointer into the element's local
(unrotated) space before calling `resizeFrame`.

The exporter uses the exact same `elementToCss()` output as CSS custom
properties. There is no second layout algorithm to drift.

### Grid mode and the type preset

There are two top-level layout modes:

- **Free (`free`)**: continuous position, size, rotation. Smart guides against
  other elements, stage centre, and margins. Snapping can be toggled with `⌘`.
- **Grid (`grid`)**: position and size snap to a modular grid (`cols × rows`,
  margin, gutter). Within grid, the user picks a preset:
  - **Modular**: rotation 0/90°, clean alignment for portfolios and collections.
  - **Type**: a baseline unit and 90° rotation steps, intended for
    letterpress/movable-type compositions. Text sits on the baseline; images and
    blocks snap to the column grid.

The two modes store the same `Frame`. Only the editing constraints differ. The
"type" intention lives inside grid as a preset, not as a third mode in the
toolbar. Changing mode or preset is non-destructive: frames are kept, then
optionally re-snapped with a confirmation.

### Text measurement and overflow

Text frames have an explicit width. The editor measures the rendered text and
fits the frame height to the content plus padding whenever text, typeface, size,
tracking, or width changes. The fitted height is saved, so selection handles and
the exported box match the text. Manual height changes remain possible and are
left alone until one of those inputs changes again. The exporter uses the same
box with `overflow: visible`.

### Editor DOM vs export DOM

|                  | Editor                                     | Export                                 |
| ---------------- | ------------------------------------------ | -------------------------------------- |
| Stage scaling    | CSS transform / zoom                       | CSS `aspect-ratio` + container queries |
| Element position | same `frameToCss` percentages              | same                                   |
| Typography       | same font sizes, scaled by stage transform | `cqw` units                            |
| Handles/guides   | overlay, not exported                      | none                                   |
| Links            | suppressed (selection instead)             | real `<a>` / `<details>`               |
| Media            | blob URLs, paused by default               | relative asset URLs, optional autoplay |
| Metadata         | inspector                                  | native `<details>` card                |

The shared styling is generated by the same token and geometry functions: the
editor's element styles and the exported stylesheet both call `elementToCss()`.
If a property affects the look of an element, it is generated once.

### Preview = export in an iframe

`buildSite(project, assetResolver)` is called for preview and export. In preview,
`assetResolver` returns `blob:` URLs, and page links carry `data-cajita-page`
instead of `href`. The iframe posts a navigate message to the parent, which
rebuilds the preview with the target page. In export, the resolver returns
relative paths and links are real. The same HTML renderer, CSS renderer, and
runtime are exercised in both modes.

This is non-negotiable because it prevents the most common creative-tool failure:
"it looked fine in the editor".

### S2 implementation notes

- Commands live in `src/lib/state/project.svelte.js`; they clone a validated
  snapshot, commit, and keep the last 40 `Project` snapshots. Pointer commands
  use a 600 ms coalesce key, so a drag/resize/rotate is one undo step.
- Selection is ephemeral and currently stored on the session (`selectedElementIds`)
  rather than a separate editor store. This keeps commands and the inspector in
  sync without a second copy of the document. The editor store holds only tool,
  snap, guides, and text-edit state.
- The S2 canvas originally implemented text and image elements. S8 now adds
  video and sound placement, inspectors, editor playback, and export.
- Page and stage frames use the same `elementToCss()` output in the editor; the
  exporter will consume it later. Text is converted to `cqw` for stage scaling.
- The canvas has no zoom/pan yet: it fits the stage into the available space, as
  the architecture recommends for the first pass.
- Custom fonts are project assets, loaded through `FontFace` in the editor and
  recorded in `project.fonts`; the bundle includes their bytes and the font
  manager enforces two fonts, unique names, and usage-safe deletion.

### S3 implementation notes

- Element links are stored on the element (`link`) and resolved through page IDs.
  `src/lib/domain/links.js` projects nodes, edges, inbound/outbound counts,
  orphans, and broken page targets; there is no edge table.
- The map view uses deterministic auto-layout (three columns maximum) and an SVG
  wire layer. Wires attach to card edges and only page links are drawn; URL and
  ficha links appear as card badges. Clicking a card switches back to the page
  view.
- Fichas are seven fixed metadata fields. The inspector edits them and renders a
  native `<details>` card; the exporter will reuse the same card markup.
- The map warning for broken links is defensive: normal project validation
  rejects a page link to a missing page, and deleting a page clears incoming
  links.
- Layers remain in the inspector while an element is selected; the map does not
  replace the layers list.

The app runs as a static web app first. A desktop shell is optional and, if it
ever happens, must reuse the same domain, UI, and platform interfaces.


- **Web** implementations use IndexedDB, `Blob`, anchor downloads, `fflate`,
  `localStorage`/`sessionStorage` for the token, and `fetch` for GitHub.
- **Desktop** implementations (future, only if a concrete need appears) use
  Electrobun RPC for folder projects, native dialogs, keychain-backed secrets,
  and local file watching. The UI does not change.
- The domain never imports a platform module. The state layer receives a
  `Platform` instance via `setPlatform()` at boot.
- Asset URLs are resolved through an `AssetUrlResolver` (`(id) => string`). The
  editor passes blob URLs; the exporter passes relative paths; tests pass
  deterministic fake paths.

### Why web, not desktop-first

- Students can use it on any machine, including locked-down labs and Chromebooks,
  with no install and no admin rights.
- The editor needs no native capability for its core loop. ZIP export works
  everywhere. GitHub's REST API supports CORS, so a fine-grained token can
  publish directly from the browser.
- **Publishing no longer requires a desktop shell.** That was the main reason to
  consider one; with PAT + CORS it works from a static web app. The remaining
  reasons are folder projects, native open/save, offline installation, and local
  file watching — all optional.
- Desktop-only would make the tool harder to hand to a class; a web app can be
  installed as a PWA later for offline use.
- If a desktop shell is ever needed, it is a thin Electrobun wrapper around the
  same static build.
- **Not Tauri** for this project: the Rust target/build directory is large and
  the machine has ~15 GB free. Electrobun's ~12 MB bundle, Bun runtime, and your
  existing comiquero experience are a better fit if that day comes. This is a
  practical choice, not a religious one; the platform interface keeps the door
  open.

### Hosting the editor itself

The editor is a static SPA; it needs no server.

- **GitHub Pages (primary):** build `dist/` and deploy it to the `cajita` repo's
  Pages. Vite `base: './'` keeps every asset relative, so it works at
  `srsergiorodriguez.github.io/cajita/` and at a custom domain without rebuilds. There is no
  client-side router, so refreshes do not 404.
- **itch.io (optional demo):** upload a ZIP whose root contains `index.html`.
  itch.io serves it inside an iframe. That is fine for trying the editor, but
  downloads, clipboard access, and pop-ups can be restricted by the iframe
  sandbox, and publishing to GitHub Pages from inside another iframe is fragile.
  Do not make itch.io the canonical install.
- **Netlify/Cloudflare Pages** are equally fine; the artifact is just `dist/`.
  No environment variables, no server functions.
- **Origin stability matters.** IndexedDB/localStorage are bound to the exact
  origin. Moving the editor from `srsergiorodriguez.github.io/cajita/` to a custom domain (or
  hosting it inside a different itch.io frame) makes existing projects invisible
  in the browser. Treat the canonical editor URL as a product decision and use
  `.cajita` bundles to migrate between origins.
- A service worker/PWA comes later; it must never cache a half-updated editor in
  a way that prevents a reload from picking up fixes.

## 9. Persistence and project bundles

### Working copy (IndexedDB)

Database `cajita`, version 1:

| Store      | Key        | Value                                      |
| ---------- | ---------- | ------------------------------------------ |
| `projects` | project id | `{ project: Project, savedAt: number }`    |
| `assets`   | asset id   | `{ meta: AssetMeta, blob: Blob }`          |
| `thumbs`   | asset id   | `Blob` (WebP/PNG, max 480 px)              |
| `settings` | key        | small JSON (last project, migration flags) |

- Autosave debounce: 600 ms after a command; flush immediately on
  `visibilitychange` and before a project switch.
- The UI shows `guardado` / `guardando…` / `error al guardar` with an
  `aria-live="polite"` region.
- Call `navigator.storage.persist()` on first project creation and show storage
  usage in the project menu. Browsers may still evict data; the UI must say so
  and push users to download a `.cajita` backup.
- Asset writes happen when a file is imported, before the element is added, so a
  failed write cannot leave a broken element.
- Deleting an asset is explicit. The default "delete element" only removes the
  reference; bytes are kept for undo. A "limpiar medios sin usar" action performs
  garbage collection and reports the freed space.

### Portable bundle (`.cajita`)

A ZIP, not a single JSON with base64. This is the backup unit: a student can
email it, put it on a USB stick, or open it next year.

```
mi-sitio.cajita
├─ bundle.json                 # manifest: format, version, asset paths, hashes
├─ project.json                # the Project document, no bytes, no file paths
├─ assets/
│  └─ <hash10>-<slug>.<ext>    # original or optimized media, one copy per hash
├─ thumbs/
│  └─ <assetId>.webp           # 480 px wireframe/poster thumbnails
└─ README.txt                  # how to reopen; app version; no tracking
```

`bundle.json`:

```json
{
  "format": "cajita-bundle",
  "version": 1,
  "createdWith": "cajita 0.1.0",
  "createdAt": "2026-10-21T23:00:00.000Z",
  "project": "project.json",
  "projectHash": "sha256:…",
  "assets": [
    {
      "id": "a_…",
      "path": "assets/4f2a9c1e-retrato.webp",
      "hash": "sha256:…",
      "mime": "image/webp",
      "bytes": 184322
    }
  ],
  "thumbs": [{ "assetId": "a_…", "path": "thumbs/a_….webp", "hash": "sha256:…" }]
}
```

Why not one JSON with base64 media:

- base64 adds ~33% to every byte before ZIP compression;
- it forces the whole project into memory as one string, so a 200 MB project is a
  200 MB+ JSON parse and a likely tab crash;
- it makes diffs, debugging, and partial recovery impossible;
- it duplicates bytes if the same image is used twice unless the app dedupes
  manually.

Binary files in a ZIP are simpler, smaller, and inspectable. `project.json`
stays tiny and can be validated on its own.

### Import algorithm

`parseBundle(bytes)` is a pure-ish pipeline over a ZIP abstraction. The UI shows
progress; the current project is not replaced until the new one is fully valid.

1. Check the compressed size and file count against limits before decompressing.
2. Read `bundle.json`; validate `format`, `version`, and the asset list.
3. Read `project.json`; run `parseProject()` (migrations + validation).
4. Check every asset referenced by the project exists in the bundle, and every
   bundle asset is referenced or intentionally unused.
5. Verify `bytes` and `sha256` for each asset. A mismatch is an error, not a
   warning; a missing asset blocks import.
6. Validate custom fonts: at most 2, unique names, 5 MB each, TTF/OTF/WOFF/WOFF2,
   and the referenced asset is `kind: 'font'`. Load each one with the FontFace API
   before committing; a font that cannot be parsed blocks the import with its
   name.
7. Check path safety: no `..`, no absolute paths, no control characters, no
   duplicate entries, no symlinks.
8. Write assets to IndexedDB under a staging prefix, then write the project, then
   remove the staging prefix in one logical commit.
9. On any failure, delete the staged assets and leave the current project
   untouched. The error lists the offending file/field.

Limits (v1): **500 MB** total uncompressed, **2,000** files, **100 MB** per file,
and a compression-ratio guard. A 500 MB bundle is already unusual for this tool;
if a project exceeds it, the user should split it or reduce video. The exact
numbers live in one config module and are tested.

### Saving and downloading

- **Descargar proyecto (.cajita)** is always available, including before export
  and publish. It builds the same bundle described above.
- The file name is `<project-slug>-<YYYY-MM-DD>.cajita`.
- Build in a worker if the bundle is large; show progress and allow cancel.
- Browser download uses a Blob URL and revokes it after the click. On Chromium,
  an optional "guardar en carpeta" can use File System Access; it is never the
  only path.
- **Abrir proyecto** accepts the file picker and drag-and-drop. If the current
  project has unsaved changes, autosave and confirm before replacing it.
- **Proyectos recientes** is a small library (IndexedDB) with title, thumbnail,
  last edited, size. It is how a student returns to a project without finding
  the file again. Deleting a project requires a confirmation and offers
  "descargar primero".
- A project is not "saved" only because it is in the browser. The UI must say
  this once, clearly, and make the download path obvious. Browser data can be
  evicted.

### Autosave, recovery, and multiple tabs

- Debounce 600 ms; flush on `visibilitychange`, before export/publish, and before
  switching projects.
- Every write increments `revision`. Keep the last **3** project JSON snapshots
  in a `backups` store (no media; media is immutable). If the main record is
  corrupt or a migration fails, offer "recuperar la última copia".
- `navigator.storage.persist()` on first project creation; show estimated usage
  and a warning when a download is overdue.
- Use `BroadcastChannel` plus a localStorage heartbeat to detect the same project
  open in another tab. Show "este proyecto está abierto en otra pestaña" and make
  the second tab read-only or ask it to reload. Never silently overwrite the
  newer revision.
- Export/publish operate on a frozen snapshot, so edits during a long job cannot
  produce a half-old/half-new site.

### Assets and media pipeline

Media is the only part of a project that grows. The policy is deliberately
simple and explainable.

**Accepted types**

| Kind  | Formats               | Notes                                                                 |
| ----- | --------------------- | --------------------------------------------------------------------- |
| image | PNG, JPEG, GIF, WebP  | SVG is rejected in v1 (script/security risk)                          |
| video | MP4 (H.264), WebM     | no transcode; poster frame generated                                  |
| audio | MP3, OGG, WAV, M4A    | no transcode; WAV can be huge, warn                                   |
| font  | TTF, OTF, WOFF, WOFF2 | max 2 per project, 5 MB each, FontFace-validated, license attestation |

MIME is sniffed from magic bytes, not trusted from the extension. An unsupported
file is rejected with a clear message before anything is stored.

**Image policy**

- **Default: optimize on import.** Non-GIF images are decoded, EXIF orientation is
  applied, the long edge is capped at **2560 px**, and the result is encoded to
  **WebP q0.85**. This is the asset stored in the project and exported. It keeps
  a class project small and is the behaviour that worked in motivomotivo.
- **GIFs are never re-encoded.** Animation is the point. Store the original bytes,
  generate a static thumbnail, and show the file size.
- **PNG transparency is preserved** by WebP alpha. If encoding fails, keep the
  original PNG rather than flatten it.
- **Originals (deferred):** v1 stores the optimized WebP as the asset. A
  "guardar original" toggle is a v1.1 feature; it would keep the original bytes
  alongside the derivative, at the cost of bundle size. Until then, the source
  file remains on the student's disk and "alta" quality is the option for work
  that needs more pixels. Do not implement the toggle in S1.
- **Maximum**: 40 megapixels and 50 MB per image. Larger files are downscaled
  (with a warning) rather than rejected outright.
- **Metadata**: EXIF is stripped from web derivatives. Credits, rights, dates, and
  provenance belong in the element's ficha, where they are visible and searchable,
  not hidden in EXIF.
- **Thumbnails**: 480 px WebP, generated once and stored. The page strip never
  loads a full-size image.

**Video and audio**

- No transcoding in v1. The browser cannot do it reliably and the tool is not a
  video editor. Store the original, generate a poster frame for video, and warn
  above 50 MB.
- `preload="metadata"` in export; no autoplay unless muted and the user opted in.
- Audio gets a small custom player and a `<noscript>` native fallback.

**Fonts**

- The six built-in OFL families are referenced by **font ID**; only the used
  families are subset to woff2 in the export. Built-in fonts are not stored in
  the project.
- **Custom fonts ship from the beginning.** A project may add up to **2** custom
  fonts, one file each, max **5 MB**, formats TTF/OTF/WOFF/WOFF2. SVG fonts are
  rejected. The font is stored as a project asset (`kind: 'font'`) and referenced
  by `project.fonts[id]`; text elements use that ID.
- Upload flow: validate the magic bytes/MIME, load it with the FontFace API to
  prove it parses, ask for a display name (unique), weight, style, and a license
  note/attestation. If it fails to load, nothing is stored.
- The user must have the right to embed the font. The UI records the attestation
  and shows a short warning; cajita cannot verify copyright. OFL fonts are fine;
  commercial fonts often need a web-embedding license.
- Export embeds the original custom font file(s) with `@font-face`, no subsetting
  (browser-side subsetting of arbitrary fonts is not reliable in v1). This is why
  the limit is small. Built-ins remain subset.
- Removing a font that is still used is blocked; the UI offers "reemplazar por
  una tipografía del paquete" first.
- Custom fonts are included in the `.cajita` bundle, count toward its size, and
  are restored on import. They are never fetched from a third party at runtime.

**Size and export**

- The project bundle keeps the stored asset. The site export includes one
  optimized derivative per used asset, named by hash.
- Show a size report before export/publish: total, largest assets, counts, and
  what will be included.
- Deduplicate by SHA-256; importing the same file twice creates one asset row and
  two references.
- Derivative cache key: `assetHash + encoderSettings`. It is not part of the
  project bundle; it can be regenerated.

**The actual GitHub limits (as of 2026)**

- GitHub warns on files over **50 MiB** and blocks files over **100 MiB**.
- GitHub recommends repositories stay under **1 GB** (under 5 GB strongly
  recommended); it is not a hard 2 GB repository cap, but a 2 GB repo is already
  a bad idea for a class.
- GitHub Pages source repositories have a recommended limit of **1 GB**; a
  published Pages site may be **no larger than 1 GB**; bandwidth is a soft
  **100 GB/month**; builds are soft-limited to **10/hour**.

Do not design up to those ceilings. Design for a small, fast site, and let the
platform limits be the final wall.

**cajita limits (v1, motivated by the above)**

| Limit                    | Value                     | Behaviour                          |
| ------------------------ | ------------------------- | ---------------------------------- |
| One media file           | 50 MB                     | reject above; warn above 25 MB     |
| Videos per project       | 3                         | block the 4th with a clear message |
| Total video              | 100 MB                    | block import that would exceed it  |
| Images per project       | 80                        | block the 81st                     |
| Audio files per project  | 20                        | block the 21st                     |
| Custom fonts per project | 2                         | block the 3rd; 5 MB each           |
| Project bundle           | 250 MB soft / 500 MB hard | warn / refuse to build             |
| Exported site            | 200 MB soft / 900 MB hard | warn / block publish               |
| Pages / project          | 50 soft                   | warn, no block                     |

These are intentionally generous for a portfolio/comic and intentionally
frustrating for a video dump. A 50 MB video limit is roughly a short clip; if a
student needs a feature-length film, cajita is the wrong tool. The UI shows a
usage meter ("2 de 3 videos · 38 MB de 100 MB") so the constraint is visible
before it is hit.

If a project exceeds the site export limit, the user can still download the
folder and host it elsewhere; cajita must not pretend GitHub Pages can take it.

**Workers and tests**

- Decoding, resizing, WebP encoding, thumbnails, hashing, and ZIP work run in a
  Web Worker when available; fall back to the main thread with a progress state.
- The pure parts (naming, manifest, dedupe plan, size limits, derivative policy)
  are unit-tested. Actual `canvas.convertToBlob()` output is verified manually;
  it is a platform adapter, not a pure function.

### Project lifecycle

- **Nuevo proyecto** creates a project with one start page and an empty stage,
  writes it to IndexedDB, and opens the editor.
- **Abrir** loads a `.cajita` bundle; **Importar** is the same path. There is no
  silent merge; a project replaces the current one after confirmation.
- **Duplicar** copies the project JSON and assets references; assets are
  deduplicated by hash, so it is cheap.
- **Eliminar** removes the project record and its unreferenced assets after a
  confirmation and an offered download.
- The project library is intentionally simple: cards with title, thumbnail, date,
  and size. No folders, tags, or cloud sync in v1.
- The bundle is the durable artifact. IndexedDB is a working copy, not an
  archive.

## 10. Export format

### Folder tree

```
mi-sitio/
├─ index.html                  # start page
├─ sobre/index.html            # every other page, one folder per slug
├─ contacto/index.html
├─ sobre-viejo/index.html      # redirect stub from project.redirects
├─ assets/
│  └─ 4f2a9c1e-retrato.webp
├─ cajita.css
├─ cajita.js
├─ favicon.svg
├─ 404.html
├─ sitemap.xml                 # only when ProjectMeta.canonicalUrl is set
├─ robots.txt
├─ .nojekyll                   # GitHub Pages
└─ CNAME                       # only if a custom domain is configured
```

Redirect stubs are tiny HTML pages with a canonical link and a meta refresh to
the new route. They are generated from `project.redirects` (max 5, FIFO), so a
recent rename after publishing does not break old links. Older renames expire out
of the queue; a live page always wins over a redirect with the same slug.

Every path is relative. The site works at a domain root, in a GitHub project
subfolder (`/repo/`), and from `file://` for a quick check. There are no absolute
`/assets/...` paths.

### Per-page HTML

The start page is the real content at `index.html`, not a redirect. Other pages
are real files, so navigation works without JavaScript and search engines can
crawl each page.

```html
<!doctype html>
<html lang="es">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Sobre — Mi cajita</title>
    <meta name="description" content="…" />
    <link rel="stylesheet" href="../cajita.css" />
    <script src="../cajita.js" defer></script>
  </head>
  <body class="fit-contain">
    <main class="stage" style="--stage-w:1200;--stage-h:800">
      <a
        class="el el-image"
        href="../contacto/"
        style="--x:12.5%;--y:18%;--w:30%;--h:42%;--rot:-3deg;--z:2"
      >
        <img
          src="../assets/4f2a9c1e-retrato.png"
          alt="Retrato de la autora"
          loading="lazy"
        />
      </a>
      <div class="el el-text" style="--x:48%;--y:20%;--w:38%;--h:18%;--z:3">
        <p>Un archivo pequeño, hecho a mano.</p>
      </div>
      <details
        class="el el-meta"
        style="--x:70%;--y:10%;--w:20%;--h:30%;--rot:2deg;--z:4"
      >
        <summary>
          <img src="../assets/8c1d0b77-sello.png" alt="Sello de la colección" />
        </summary>
        <div class="meta-card">…</div>
      </details>
    </main>
  </body>
</html>
```

Notes:

- Inline custom properties are the **only** inline style allowed. They are
  generated by `elementToCss`, not typed by users.
- Text is HTML-escaped. URLs are sanitised to `http:`, `https:`, `mailto:`,
  `tel:`; `javascript:` and `data:` links are rejected.
- `alt` is required for images; the inspector warns when it is empty. Decorative
  images can be explicitly marked decorative (`alt=""`).
- Each page has exactly one visible `<h1>`: the text element marked `heading:
true`, or a visually hidden `<h1>` with the page title when there is none. The
  page title is always the `<title>`. This keeps the outline valid without forcing
  a heading into the composition.
- Metadata is native `<details>`; no JS needed to open it. JS adds Escape-to-close
  and backdrop behaviour.
- Audio uses a styled button plus `<audio>`; a `<noscript>` fallback shows native
  controls. Video uses native `<video controls playsinline>`.
- Autoplay is muted-only and gracefully degrades; browsers may block it.

### CSS strategy

- One stylesheet, generated from the site theme tokens plus per-element classes.
- Stage shell: a flex row whose `justify-content` is `center` or `flex-start`
  according to `stage.align`; the page background fills the rest of the viewport.
- Stage: `aspect-ratio: var(--stage-w) / var(--stage-h)`,
  `container-type: size`, `overflow: hidden`.
- `width` fit:
  `width: clamp(var(--stage-min), 100vw, var(--stage-max))`.
  The page scrolls vertically when the stage is taller than the viewport. If the
  viewport is narrower than `minWidth`, the shell scrolls horizontally instead of
  shrinking text into illegibility. `minWidth` is a floor, not a promise.
- `contain` fit:
  `width: min(var(--stage-max), 100vw, calc(100svh * var(--stage-ratio)))`.
  The whole stage is visible and letterboxed; horizontal alignment follows
  `align`. `minWidth` is ignored here because fitting the height is the point.
- Element positions/sizes: percentages of the stage; content scales
  proportionally with the stage. There is no reflow and no breakpoint.
- Font sizes: `pxToCqw(fontSize, stageWidth)` so typography scales with the stage.
- Rotation: `rotate(var(--rot))`.
- Fonts: built-in families actually used are included as subset woff2; custom
  fonts are included as their original TTF/OTF/WOFF/WOFF2, only when used. Both
  use `font-display: swap` and a sensible fallback. `@font-face` paths are
  relative. A custom font that fails to load falls back to the site pairing, never
  to invisible text.
- `prefers-reduced-motion` disables page transitions and hover lifts.
- Focus styles are visible on links, summary elements, audio buttons, and video.

### Runtime JS (progressive enhancement only)

`cajita.js` is a small vanilla script (< 5 KB gzipped) that:

- plays/pauses audio elements and updates their button state;
- closes metadata cards on Escape/backdrop and manages focus return;
- adds a fade/slide transition on navigation when supported;
- in preview mode only, posts navigation messages to the parent.

It does **not** render content, compute layout, or require a framework. If it
fails to load, the site still reads and navigates.

### Determinism and file names

- Asset file names are `<sha256[0..10]>-<slugified-original>.<ext>`, so identical
  bytes dedupe and renamed originals do not churn URLs.
- File order is stable (pages in project order; assets sorted by id/path).
- No build timestamps in HTML/CSS. `sitemap.xml` (only when
  `ProjectMeta.canonicalUrl` is set) uses page order, not `now`.
- `buildSite()` returns a manifest with `path`, `bytes`, and `mime`; the ZIP
  writer and the folder writer consume the same manifest.
- An export with no pages is rejected with `EXPORT_EMPTY`.
- Warnings (missing alt, huge assets, duplicate slugs) are returned with the
  manifest and shown before download/publish.

### Single-file export

Deferred to v1.1. It is useful for "one HTML postcard" sharing, but it requires
inlining every asset as a data URI, has browser size limits, and duplicates the
primary pipeline. The folder/ZIP export is the canonical output.

## 11. Publishing to GitHub Pages

### Auth for v1

**What a PAT is, in plain language.** A Personal Access Token is a long random
string generated by GitHub that lets a program act on your account with the
permissions you choose. It is not your password; it is a limited key you can
revoke. cajita sends it only to `api.github.com` over HTTPS, and never stores it
in the project, the exported site, or a server.

**How a student creates one:**

1. GitHub → Settings → Developer settings → Personal access tokens →
   **Fine-grained tokens** → Generate new token.
2. Select only the repository they will publish to (or all repositories only if
   they want cajita to create a repo).
3. Repository access: select this exact repository (or all repositories).
   Permissions: **Contents: read/write** and **Pages: read/write**.
   For organization repositories, authorize the token with SSO.
   **Administration: read/write** is needed only if cajita should create the
   Pages site automatically. Without it, enable Pages once manually in the
   repository settings; cajita can then update the `gh-pages` branch and skip
   Pages creation.
4. Set a short expiration (30–90 days) and generate.
5. Paste it into cajita's publish panel. Use "recordar en este dispositivo" only
   on a personal machine.

Security rules:

- Treat it like a password. Never paste it into a shared document or the class
  chat; never commit it.
- If it leaks, revoke it on GitHub immediately. Regenerating is cheap.
- Use one token per student, scoped to their own repo. Do not give students a
  shared teacher token.
- cajita stores it in `sessionStorage` by default; "recordar" moves it to
  `localStorage`. A "olvidar token" button clears it.
- The token is never written to the project, the `.cajita` bundle, the exported
  site, or logs.
- **Device flow is not available in the web build** because
  `github.com/login/device/code` does not send CORS headers for browser requests.
  A proxy or a desktop shell could offer it later. v1 uses PATs.
- If a student cannot or does not want to create a token, **download the ZIP and
  upload it manually** is a first-class path, not a failure.

### Repository setup

- v1 targets an existing **public** repository. GitHub Pages for private repos
  requires a paid plan; do not assume it.
- The user creates an empty repo (no README needed), then pastes
  `owner/repo` into cajita. Creating the repo from the app is optional
  convenience, not required.
- The generated site lives on the `gh-pages` branch, at the branch root. This
  keeps it isolated from any source code on `main`.
- Project pages are served at `https://<owner>.github.io/<repo>/`. A custom
  domain writes a `CNAME` file and requires the corresponding DNS records; the
  UI explains that it is optional and cannot verify DNS from the browser.
- Enable HTTPS in the repo's Pages settings (GitHub does this by default for
  `github.io`; custom domains need the certificate to finish provisioning).

### Publish flow

1. **Plan** (`domain/publish/plan.js`): compare the local file manifest hashes
   with a locally cached manifest of the last successful publish. Produce
   `uploads`, `deletes`, `unchanged`.
2. **Check the repo**: v1 targets an existing public repo. If it does not exist,
   cajita asks the user to create it on GitHub and paste the URL. Creating it
   from the app is an optional convenience that requires **Administration:
   read/write**; it is not required for the core flow.
3. **Write the tree** with the Git Data API:
   - create blobs for changed files;
   - create a tree with `base_tree` for updates (deletions use `sha: null`);
   - create a commit with the previous commit as parent (or a root commit when
     creating the branch);
   - update `refs/heads/gh-pages` non-forcefully.
     Using `gh-pages` isolates the generated site from any source code the user may
     keep on `main`.
4. **Enable Pages**: `POST /repos/{owner}/{repo}/pages` with
   `source: { branch: 'gh-pages', path: '/' }`; if it already exists, `PUT`/`PATCH`
   the source. A `.nojekyll` file is always included.
5. **Poll** `GET /repos/{owner}/{repo}/pages/builds/latest` with backoff until
   `built` or `errored` (timeout ~120 s). Report the public URL
   `https://<owner>.github.io/<repo>/`.
6. **Cache** the published manifest locally (not in the repo) for the next diff.

The pure request builders are tested against recorded fixtures. The transport is
a thin `fetch` wrapper with `Authorization: Bearer <token>`, `Accept:
application/vnd.github+json`, and `X-GitHub-Api-Version: 2022-11-28`.

### Unpublish and privacy

- Publishing makes the site **public**. The publish dialog must say this in one
  plain sentence, not bury it in a help link. The repo can be public even if the
  site is later unpublished; history remains.
- **Despublicar** calls `DELETE /repos/{owner}/{repo}/pages`, which removes the
  Pages site but does not delete the repository, its branches, or its commit
  history. cajita explains that and offers a link to the repo settings.
- Deleting the repository itself is a manual GitHub action. cajita must not offer
  a one-click "delete my repo" in v1; too destructive.
- A student who wants a site offline temporarily can unpublish and republish
  later; the `.cajita` bundle remains local.

### Failure handling

| Case           | Code                  | UI response                                                             |
| -------------- | --------------------- | ----------------------------------------------------------------------- |
| 401            | `PUBLISH_AUTH`        | "El token no es válido o caducó"; link to revoke/create                 |
| 403 on Pages   | `PUBLISH_PAGES_SETUP` | Files uploaded; explain manual Pages setup or Administration permission |
| 409/422 on ref | `PUBLISH_CONFLICT`    | Offer "reintentar" and show the branch state                            |
| Network/CORS   | `NETWORK`             | Keep the export available; suggest ZIP download                         |
| Build errored  | `PUBLISH_BUILD`       | Link to the Pages build log; site files are still uploaded              |

The user can always fall back to **download ZIP** and upload it manually. That is
the escape hatch, not a hidden failure mode.

### S5 implementation notes

- `buildSiteEntries()` is the single file tree shared by ZIP export and publishing.
- `domain/publish/plan.js` parses `owner/repo` URLs, hashes files with SHA-256,

- `domain/publish/github.js` contains pure request payloads and API paths.

- First publish creates an initial commit and `refs/heads/gh-pages`; later
  publishes update the ref non-forcefully. Unchanged blobs reuse cached SHAs.
- Pages is created or updated for `gh-pages` at `/`; the latest build is polled

- The publish cache (path → hash + Git blob SHA, public URL) lives in

- PAT storage is session-only by default; “recordar” moves it to `localStorage`.
  It is never written to IndexedDB, the bundle, or the site.
- Unpublish is `DELETE /pages`; it does not delete the repository, branches, or

### S9 implementation notes

- Page transitions use the native cross-document View Transitions API. The
  exported page sets `data-transition="cut|fade|slide"` on `<html>`; the shared
  CSS opts into `@view-transition { navigation: auto; }` and styles old/new root
  snapshots for 1000 ms.
- There is no link interception. Unsupported browsers and `prefers-reduced-motion`
  simply navigate without animation. Preview opens on the active editor page and
  animates the outgoing page wrapper for fade/slide, but cannot animate the
  incoming document itself.
- Publish history is stored in `project.publish.history`, capped at 5 entries.
  Successful publishes record date, owner/repo, branch, URL, commit SHA, and
  upload/delete/unchanged counts. Unpublishes record date, owner/repo, and branch.
- History contains no token. It travels in the `.cajita` bundle. There is no
  rollback; each commit links to GitHub.
- Failed attempts are intentionally not recorded; otherwise the history becomes a
  noisy error log.
- GitHub API requests use `cache: 'no-store'` so a ref read cannot be stale after a
  publish. If the branch still moves between read and update, the publisher
  re-parents the same tree on the fresh tip and retries the ref update once.

### S10 implementation notes

- Video imports are capped at 20 MB per file. This is deliberately lower than
  the 50 MB general file cap because the GitHub Git Blob API sends base64 inside
  a JSON request; large videos fail at the API boundary rather than at the repo
  file limit. Audio/images keep the general cap.
- Embeds are one element type with `provider: 'youtube' | 'observable'` and a
  canonical source URL. No raw HTML is stored. Provider parsers normalize URLs
  and exporter metadata supplies sandbox/allow rules.
- The editor renders an embed placeholder; only preview/export load the iframe.
  YouTube uses `youtube-nocookie.com`; Observable uses its `/embed/` URL.
- Preview pages load through `public/preview.html`, a real same-origin shell that
  accepts rendered HTML over `postMessage` and replaces its document. This keeps
  a usable HTTP referrer for YouTube; blob preview pages produced error 153. The
  shell re-registers its listener after `document.open()`.
- Embeds have no link/ficha interaction: the iframe is already interactive and
  nesting it in an anchor/details would be invalid. A source link is rendered
  inside the frame.
- Medios is a horizontal strip with fixed-width tiles.
- Pages polling waits for a build whose `commit` matches the newly published
  commit, so a previous `built` result is not treated as success.
- The localStorage tab lock keeps its heartbeat, but the banner exposes an

### S11 implementation notes

- `shape` is a first-class element with `shape: circle | square | triangle`,

- One **Forma** tool opens a small inline picker; it does not add four permanent

### S20 implementation notes

- `platform.files.readCollectionZip` reads a ZIP without touching project state.
  It ignores hidden/`__MACOSX` entries, prefers `fichas.csv` when several CSVs

  enforces image count/size guards.

  image entries become `File` objects and pass through `importMedia`, preserving
  the normal compression/hash/dimension/limit pipeline. The CSV is then
  revalidated against the updated assets and imported with the existing

  case-insensitive and basename-aware.
- If media import fails, records are not written; already-added media remains in
  Medios for a retry. No schema is inferred from the ZIP.

## 12. Extensibility and customization

The goal is **extension seams**, not a third-party plugin runtime. In v1, plugins
are build-time modules registered at boot: no arbitrary code from a project file
or a URL is executed inside the editor, and no plugin JavaScript is shipped to
visitors. The exported site stays static HTML/CSS/JS generated by cajita.

### Registries

| Seam              | What it registers                                              | v1 status                        |
| ----------------- | -------------------------------------------------------------- | -------------------------------- |
| Element kinds     | default frame, editor renderer, inspector, exporter, validator | core: image, text, video, audio  |
| Importers         | detect/parse/preview/commit a file                             | `.cajita`; CSV collections later |
| Exporters         | site folder/ZIP, project bundle                                | v1; single-file later            |
| Site themes       | token set + font pairing                                       | six shipped themes; data-only    |
| Publish providers | GitHub Pages, future SFTP/Netlify                              | GitHub Pages only                |
| Templates         | starter projects                                               | demo/template later              |
| Font sources      | built-in pack + project custom fonts                           | both from v1                     |

An element kind is the most important seam. A future `collection-item` kind can
add its own frame defaults, inspector fields, metadata card, and export markup
without changing the page/geometry model. A CSV importer can create collection
items and a page template using the same model; it does not need a separate app.

### Rules

- A plugin may import `domain/` and `platform/` interfaces, never Svelte
  internals, the project store, or `window` directly.
- Every plugin output goes through the same validation and export pipeline.
  Plugins do not write HTML strings into the page; they return model data.
- The project schema is versioned. Unknown _top-level_ fields are preserved on
  load/save so a newer project can round-trip through an older editor, but an
  unknown element kind is not rendered: it is reported, not silently dropped.
- No plugin can add a script tag to the exported site. Custom behaviour must be
  expressed as data and handled by the core runtime.
- The plugin surface is documented but **not public API-stable in v1**. Prefer
  refactoring a core module over designing a generic extension framework before
  the first real collection importer exists.

### Customization from the beginning

These are core features, not plugins:

- **Custom fonts:** up to two uploaded TTF/OTF/WOFF/WOFF2 families per project,
  stored as assets, loaded with FontFace, exported with `@font-face`, included in
  the bundle. Validation and licensing attestation as described in §9.
- **Site theme:** one of six palettes + font pairing, with custom background,
  ink, and accent colours checked for contrast.
- **Stage:** presets plus custom width/height, fit, alignment, min/max rendered
  width.
- **Page:** background colour/image, texture, transition.
- **Element:** frame, rotation, opacity, z-order, border, shadow, blend mode,
  image fit/pixelated, typography, audio/video controls.
- **No raw CSS/HTML.** Customization is a set of typed controls, not a code
  escape hatch. This keeps the export accessible, safe, and visually coherent;
  raw code is the opposite of the constraint-based premise.

PWA and desktop shells are explicitly later. The platform interface and the
static build keep those doors open without paying their cost now.

## 13. Internationalization

- **Two locales:** `es` and `en`. **Spanish is the default**, with an ES/EN
  switch persisted per device. Do not auto-detect from the browser in v1.
- **UI locale is a device preference**, not a project property. The exported
  site's language is `project.locale`, which is independent: a student can run
  the editor in English and publish a Spanish site.
- **All strings go through `t(key, params)`.** No hardcoded UI copy, including
  `aria-label`, `title`, empty states, errors, and toasts. The only exceptions
  are user content and proper nouns.
- **Key parity is a test, not a type system.** `en.js` is the source of truth;
  `es.js` must have the same keys and placeholders. The parity test fails on a
  missing key, an extra key, an empty value, or a placeholder mismatch. JSDoc
  documents the dictionary shape without adding a TypeScript build step.
- **Placeholders:** `{count}`, `{name}`, `{url}`. A parity test checks that both
  languages use the same placeholder set.
- **Dates/numbers:** `Intl.DateTimeFormat` / `Intl.NumberFormat` with the UI
  locale. Do not hand-format.
- **Exported UI labels** (audio play, metadata close, collection labels) use the
  **site locale**. Content is not machine-translated. Bilingual sites are a
  later feature: page-level `lang` plus optional translations, with a language
  switcher generated by the exporter.
- **Copy tone and casing:** sentence case in Spanish and English for headings,
  titles, and sentences — capitalize the first word only, except proper nouns
  (`GitHub`, `S0`). Never Title Case. Buttons, tabs, and micro-labels may be
  lowercase by design. Errors say what happened and what to do, not "¡Ups!".

## 14. Accessibility

Editor:

- Every control is keyboard reachable, with a visible focus ring (2 px blue,
  2 px offset).
- Icon-only buttons have an `aria-label` and a tooltip with the same text.
- Native `<dialog>` for modals; focus is trapped by the platform, Escape closes,
  focus returns to the trigger.
- The stage is pointer-first, but every element is also available in a **Layers**
  list in the inspector (select, reorder, lock, hide). This is the keyboard and
  screen-reader path to the canvas.
- Save/export/publish status is announced with `aria-live`.
- `prefers-reduced-motion` removes non-essential motion.

Exported site:

- Real links, real headings, `alt` text, `<details>` metadata, native video
  controls, keyboard-operable audio.
- Colour is never the only signal; link targets are announced.
- The stage scales but does not disable browser zoom. Text remains selectable.
- A "skip to content" link is included on every page.
- No hover-only information: metadata is click/focus accessible.
- Contrast is checked for all shipped themes; user custom colours get a warning,
  not a silent failure.

## 15. Performance budgets

- Initial app JS: **< 250 KB gzipped** (excluding fonts).
- App CSS: **< 30 KB** uncompressed.
- UI fonts: 2 families, subset, preloaded; content fonts loaded on demand.
- Editing 100 elements on one stage: pointer interactions stay near 60 fps on an
  M1 / 8 GB machine; no per-frame history snapshots.
- Export of a 20-page, 50 MB site: **< 3 s** to build the file tree, plus ZIP
  time; progress is visible. Move ZIP compression to a worker if it blocks.
- Thumbnails: generated at import/update, max 480 px, stored as WebP/PNG; never
  load full-size images just for the page strip.
- The app must remain usable at 1280 × 800 (the common classroom laptop).
